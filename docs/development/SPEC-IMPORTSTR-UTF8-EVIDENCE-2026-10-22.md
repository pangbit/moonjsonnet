# Importstr UTF-8 substitution and host-boundary evidence

**Decision: the bounded BOM-free UTF-8 text-substitution contract is reviewed
complete for the pinned native toolchain.** Valid supplied data becomes its exact
Unicode text without Jsonnet parsing or normalization; malformed input is rejected
under the validity requirement and the embedding API's strict UTF-8 policy.
This does not complete importstr loading, the whole CORE-IMPORT row or arbitrary
host behavior. The [pre-execution criteria](SPEC-IMPORTSTR-UTF8-REVIEW.md) fix the
normative source, input domain and exclusions independently of the outcomes.

The fixed Core Syntax lines 915-916 require valid UTF-8 and string substitution;
the language reference defines strings as Unicode-codepoint sequences. Those
statements do not prescribe ErrorKind, exact diagnostics or failure-cache policy.
Initial UTF-8 BOM interpretation is explicitly **unknown** in this review, rather
than inferred from the installed decoder or counted as passing. Interior U+FEFF
is included as ordinary data. No API, interpreter or dependency implementation
was changed to obtain these results.

## Why the host entry point matters

The reusable Evaluator binary importer supplies bytes for all three import forms,
as documented in [the API](../reference/API.md#reusable-evaluator). Its ImportReader
load_data keeps bytes; load_text applies the strict UTF-8 decoder. The raw
importstr branch then constructs Str(source.text) without parsing code. A
Source.text callback instead supplies already decoded text: older IR3 proves
opacity, not rejection of malformed byte sequences. The one-shot Program.evaluate
API keeps its separate text/binary resolver modes; this batch does not change
that contract or require hosts to surrender their own I/O/identity policy.

The first test adapter incorrectly passed only a one-shot binary resolver to
text imports and produced **14/17**, with three failing groups. Valid imports were
disabled, and the first invalid-byte case failed a diagnostic-location check;
these are retained setup failures, not evidence of incorrect UTF-8 substitution.
The tests were corrected to use Evaluator.set_importer(binary_resolver), without
changing the byte/text oracles. The focused selection then passed **17/17**.
Both logs and the initial adapter source remain identified below; the initial
run is not silently reclassified as passing.

Structural review covers the reader's strict decoder and the no-parser raw branch.
The installed native core decoder declares explicit one-to-four-byte ranges,
excludes overlong/surrogate/out-of-range forms and raises on unmatched sequences.
The native dependency includes a compiler intrinsic; boundary executions and
reviewed source support this engineering decision, not a separately machine-checked
proof of the compiler/runtime or acceptance of every host input representation.
